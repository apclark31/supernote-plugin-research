| B-012 | Resolved | Gesture unreliability was `_enabled` flag leak, not phantom pointers | Phantom pointer events after sleep are real (digitizer noise) but were a **red herring** for the primary reliability issue. The SDK's motion listener naturally stops receiving events when the RN plugin view is visible (touch interception). Only `_configOff` (user settings) remains. |

| B-019 | Fixed (awaiting on-device test) | Gesture detector permanently dies after SDK calls hang | SDK calls in the gesture path can hang indefinitely (plugin view showing, system dialogs). A handler awaiting the hung promise holds `_actionInProgress = true` forever; `onMsg`'s `if (_actionInProgress) return;` then drops ALL future events. **Session 33 fix (`withTimeout`, 5s) was insufficient on its own**: JS timers are suspended while the plugin view is closed (documented on-device learning), which is exactly when gestures run -- the timeout may never fire. **Session 34 fix: event-driven watchdog in `onMsg`** -- if `_actionInProgress` has been held > 8s, the next motion event force-clears it (the motion stream is the one thing guaranteed to keep flowing while the view is closed). An action token (`_actionId` via `beginAction()`/`endAction()`) prevents a hung handler's late `finally` from clobbering a newer action's guard. Worst case is now one dropped gesture, never a dead session. `withTimeout` retained as a first line of defense for when timers do run. |
| B-020 | Fixed (awaiting on-device test) | Native element leak when `getElements` times out in gesture scan | When `withTimeout(getElements(...))` timed out, the underlying promise kept running; if it later resolved, the returned elements were never `recycle()`d -- each timeout leaked a page's worth of native-side element memory. On a device with intermittent SDK hangs this compounds over a session and may have contributed to device degradation. Fix (session 34): on timeout, attach a continuation to the original promise that recycles late-arriving elements. |
| B-022 | Fixed (awaiting on-device test) | No fetch timeout + `_inflightPromise` poisoning permanently kills task loading | **Critical.** `todoistFetch` (`todoist.js:43`) has no timeout/abort. `taskCache.js` stores the pending promise in `_inflightPromise` and clears it only in `finally` -- if a fetch hangs (wifi drop mid-request), the promise never settles, `_inflightPromise` never clears, and every future `fetchTaskData()` joins the same dead promise for the life of the process (days). TaskHome stuck on "Loading tasks..." forever; gesture prefetch shares the poisoned promise. Also: retry backoff uses `setTimeout` (`todoist.js:40`), which is suspended if the view closes mid-backoff, stalling the chain. Fix: AbortController timeout on all fetches + clear `_inflightPromise` via a race-with-deadline (not just `finally`). Found in session 34 audit. **FIXED session 34 pass 2:** `fetchWithTimeout` (AbortController, 20s) in todoist.js with retry on timeout/network error; `taskCache` abandons in-flight fetches older than 90s via identity-checked slot (timer-free backstop). |
| B-023 | Fixed (awaiting on-device test) | Lasso elements never recycled in QuickAdd/Capture/ocr.js -- native memory leak on every capture | **Critical for device stability.** `QuickAdd.tsx:134` and `Capture.tsx:129` call `getLassoElements()` and never call `.recycle()` on any path (success or error); `ocr.js` doesn't recycle the array it receives either. (TaskHome and gestureDetector recycle correctly -- these are the only offenders.) Found in session 34 audit. **FIXED session 34 pass 2:** shared `recycleElements()` in ocr.js; QuickAdd and Capture recycle in `finally` on every path. |
| B-024 | Fixed (awaiting on-device test) | Untimed SDK awaits freeze screens while holding guard flags (duplicate-task risk) | **High.** (1) `TaskAdd.handleSubmit`: `setLassoStrokeLink`/`saveCurrentNote` awaited with no timeout AFTER `createTask` succeeds and before `setSubmitting(false)` -- a hang leaves the button stuck on "Adding…" and a retry creates a duplicate Todoist task.
